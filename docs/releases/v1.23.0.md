# v1.23.0 - One mode, and it cannot be taken away from you

The adapter now has exactly one mode: the **Datalogger**. It is built into the firmware. Nothing can change it - not a setting, not a config file you upload, not a tool on your PC, not a bad value left behind by something that crashed.

Two other things got fixed along the way: a logger that happily recorded a parked car for twelve hours, and a Wi-Fi drop that took eleven seconds to recover from.

## In short

| What changed | What you will notice |
|---|---|
| The mode setting is gone | The adapter can never again be stuck "not logging" |
| The recording gate was fixed | Trips start when the engine starts, and **end when it stops** |
| Wi-Fi recovery was fixed | Back on the network in milliseconds, not ~11 seconds |
| Event log wording | Plain sentences instead of engineer shorthand |

⚠️ **You need NC Flash v2.9.0 or newer.** Older versions cannot reach your ECU after this update. Details at the bottom.

## One mode (issue #92)

### What was wrong

The adapter used to read a single word out of its config file to decide what to do. `poll_log` meant "be a Datalogger". A few other words meant other things.

If that word ever ended up wrong, the adapter **stopped logging and looked completely healthy while doing it**. Wi-Fi connected. SD card mounted. No errors anywhere. You only found out when a drive produced no data.

That happened for real. And it was never you setting it - the PC tool wrote that word.

The code reading it had a second trap. It compared against four known values, and **anything it did not recognise quietly fell through to a mode where the datalogger does not run**. A typo, a half-written file, or a word from a newer firmware would all silently kill your logging.

### What we did

We did not add checking. We deleted the word.

The adapter does not read it any more, so nothing can set it wrong. Upload a config file that says `slcan`, or `elm327`, or `potato` - the adapter accepts the file, ignores that line, and runs the Datalogger.

Removed along with it:

- **`port` and `port_type`**, and the CAN-over-TCP server they configured. Nothing fed data into that server and nothing read data out of it.
- **The CAN section in Settings.** There was nothing left in it that did anything.
- **The "Restore Datalogger mode" button** and its warning banner. They existed to rescue an adapter stuck in the wrong mode. That cannot happen any more, so the rescue is not needed.

### Your ECU flashing is not affected

NC Flash talks to the adapter on a fixed, always-on channel that has nothing to do with any of this. Those files were not touched at all - the code that actually writes to your engine computer is byte for byte the same.

## The logger no longer records a parked car (issue #134)

### What was wrong

The datalogger would start itself with the engine stopped. And once started, it never stopped. One bench session recorded **347 MB of a stationary car over twelve hours**.

Three separate faults, all growing from one confusion in the code.

The worst one was circular. An open recording **forced** the "is the engine running?" answer to yes. So the adapter was using "we are already recording" as proof that "the engine is running" - which is what kept it recording. A loop with no way out.

The second one explains a pattern you may have seen. A missing RPM *answer* was mistaken for a missing RPM *channel*, so the adapter gave up on RPM and judged the engine by battery voltage alone. That happened after **any** pause longer than two seconds - a flash session, a bus claim, a recovery. It is why logging kept restarting itself after every time you used NC Flash.

### What we did

The two questions are now kept apart, because they are genuinely different questions:

- **"Is the engine running?"** - answered only by voltage and RPM.
- **"Should we sample fast?"** - answered by the engine, *or* by you pressing Start.

So an automatic trip now starts when the engine actually starts, and **ends when it stops**. Pressing Start manually still records at full speed; it simply no longer claims the engine is turning when it is not.

> ⚠️ **This one is proven on the bench but not yet on a real drive.** If an automatic trip starts or ends at a strange moment, that is the thing worth reporting.

## Wi-Fi comes back fast after a drop (issue #135)

### What was wrong

When the link dropped, the adapter did not try to reconnect right away. Recovery was left to a background task that woke up every 5 seconds, and then waited another 5 seconds before acting.

Worst case: **about 11 seconds off the network** for every drop.

The log was also misleading. When a join simply failed - the access point never answered - the log described it as something the adapter had done to itself.

### What we did

The adapter now notices the drop the moment it happens and reconnects in milliseconds instead of waiting for the next wake-up. The log says what actually happened rather than guessing.

**One thing we did not fix, honestly stated:** some boots show a drop at around the 8-second mark. We re-investigated it and the previously recorded cause turned out to be wrong - it is the radio's own give-up timer on a join the access point never answered. It happens about **2 boots in 55**. That is ordinary 2.4 GHz behaviour, and it is not something this firmware can fix.

## Clearer event log (issue #133)

If the PC tool disappears in the middle of a flash, the adapter notices and takes the bus back. It used to report that like this:

```
REAPER_RESUME auto-resume: host gone (ttl_expired socket_dropped) diag_idle=35557ms mid_claim
```

Now it says:

```
AUTO_RESUME  the PC tool vanished during a flash -- bus released, logging again (quiet 35.5 s)
```

Wording only. No timing, no condition and no recovery logic changed. Logs already saved on your SD card still display with the right colours.

## Two things to know before you upgrade

### You need NC Flash v2.9.0 or newer

Older versions worked by switching the adapter into `slcan` mode. There is nothing to switch into now, so **they cannot reach your ECU at all**.

They fail cleanly - they cannot half-write your engine computer - but they will not work. If you are on v2.9.0 or newer, nothing changes for you; it already flashes without touching the mode.

### Going back to older firmware is safe, and stays safe

Old firmware refuses to load a config file that is missing certain lines. And when it refuses, it **wipes the file and starts fresh** - which would take the adapter off your Wi-Fi and leave you holding the button to recover it.

Rolling back is the normal thing to do when a new build misbehaves, so it must not be the thing that wipes your settings. This firmware keeps writing those lines into the file, at fixed values, purely so an older build can still read it. They do nothing here.

**That safety net is temporary. It is removed in v1.25.0.** From that version on, a backup you take can only be restored on v1.23.0 or newer. The downloaded file carries its own reminder in a `_deprecated` line, so you do not have to remember this.

## How it was tested

Everything below was done on the bench adapter, over Wi-Fi, on a live CAN bus:

- Wrote `"protocol":"slcan"`, `"port":"35001"`, `"port_type":"udp"` into the adapter's **real** config file - the one it reads at startup - and rebooted it. It came up as a working Datalogger, polling the engine computer. **The issue #92 failure is now impossible rather than repaired.**
- Four NC Flash claim / park / release / resume cycles, all clean. The ECU flashing channel answered normally throughout.
- Saved a setting from the web page and confirmed it reached the adapter, including the lines that keep a rollback safe.
- Several reboots and firmware updates with **zero unexpected resets**, SD card mounted the whole time.
- Every setting survived: Wi-Fi, access point, sleep voltage, sleep time, engine voltage, wake-on-CAN, time zone, and all seven saved passwords through a full download-and-upload round trip.

Roughly 550 lines of code were deleted in this release. The files that carry out an ECU flash were not touched at all.
