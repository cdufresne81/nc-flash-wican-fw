# v1.19.1 - The adapter stops playing dead when it wakes up

If you have switched the ignition on and thought the adapter had not come up — no blue light, not on Wi-Fi, nothing — this release fixes the cause. It was awake the whole time. It was recording your drive. It just could not show you.

## What you saw

Three things, reported together, that turned out to be one bug:

1. **Ignition on, and the adapter looks dead.** No light, unreachable on Wi-Fi. Then you open the log later and find it was recording perfectly the entire time.
2. **Wi-Fi seems to connect only after the trip ends**, sometimes seconds after the log file closes.
3. **`MIC chip would not sleep after 2 nudges`** appearing in the event log, over and over.

## What was actually wrong

Waking up took **20 seconds**, and everything you can see — the light, the Wi-Fi, the web page — was queued up behind it. Recording was not: it restarts in a couple of milliseconds. So the adapter genuinely was recording while genuinely looking dead. Both halves of that were true at once, which is exactly why it was so confusing.

The 20 seconds were not spent doing anything. They were spent **waiting for a lock that was never going to be free**, twice over — ten seconds, give up, ten seconds again, give up. The adapter never even spoke to the OBD interpreter chip.

Something was holding that lock: a piece of the old ELM327 support that **should not have been running at all**. This adapter uses its own faster polling system and does not need it, but it was being started anyway, in every mode. It would take the lock, wait for data that had already been thrown away, and then hold it — through the whole sleep and into the wake.

The third symptom is the same lock. When the adapter tries to put the interpreter chip to sleep, it needs that lock too. It could not get it, so the chip was never actually asked to sleep — and the adapter then blamed the chip in the log. That message was accusing something innocent.

Whether it happened on any given wake came down to timing, which is why it felt random: roughly half the time.

## What it does now

**Waking up takes about 1.4 seconds instead of 20.** Measured in a real car, four times in a row, on the same number every time — the variability is gone because the thing causing it is gone.

**The old ELM327 reader is no longer started when nothing can use it.** It still runs in the modes that genuinely need it. This also gives back 16 KB of the adapter's scarcest memory.

**A stuck lock can never cost 20 seconds again.** Even if something else holds it in future, the wake now gives up in about a second and carries on instead of waiting twice for nothing.

**The log stops blaming the chip.** If the adapter cannot get the lock, it now says so and names what is holding it, instead of reporting a chip fault that never happened.

Along the way this also fixed a slow memory leak that happened on every single wake, and a bug where a short reply could hand an ELM327 app a few bytes of junk on the end.

## Also in this release: turning on **debug** no longer bricks the adapter

This one is important if you ever use the **debug** setting.

Switching **debug** on could put the adapter into an endless reboot loop — a crash about 13 seconds after every start, forever. The only way out was safe mode. Turning the setting off again was not possible, because you could no longer reach the adapter to turn it off.

The cause: the part of the system that handles Wi-Fi events was given a very small working area by default, and writing a log line from inside it needs more room than that. One single connection attempt was enough to run off the end. It had nothing to do with weak Wi-Fi — it happened just as reliably with the adapter sitting next to the router.

**This bug was already there before this release.** It was not introduced by the wake-up fix above; it reproduced exactly the same way on v1.19.0. It only stayed hidden because nobody had switched **debug** on at the wrong moment.

The working area has been made twice as large, which fixes it. A proper fix — not writing log lines from that part of the system at all — is written up as follow-up work, because making the room bigger stops this particular crash but does not stop a future log line from doing the same thing again.

## Also in this release

**The event page is quieter.** Detailed wake-up timings are now hidden unless you switch on the **debug** setting. Anything that reports a *problem* is still always shown — failures are never hidden behind a setting.

**The adapter waits a little longer before deciding the interpreter chip ignored it.** The chip reliably takes about 4 seconds to settle; the old limit was about 4 seconds, so it was a coin toss. Now there is real margin.

## Honest notes

This was found and confirmed with measurements taken in the car, not from reading code — the adapter now records exactly where its wake-up time goes, and those numbers are what identified the culprit.

Two known things are deliberately left for later, neither affecting normal use: the light still cannot come on until the wake finishes (that needs a separate change), and one piece of tidy-up in the shared UART handling is better done on its own rather than bolted onto a tested fix.

Your recorded data was never at risk at any point. The datalogger talks to the car directly and never touches the part of the system this bug lived in.
