# v1.22.2 - The datalogger starts itself again after an interrupted flash

One fix. If NC Flash disappears in the middle of a session, the adapter now notices and goes back to logging by itself - **even with the engine running**, which is the one case where it never used to.

## The problem

When NC Flash takes control of the adapter, it puts the datalogger on hold so the two are not talking on the wire at once. It hands control back when it is done.

If it never gets to hand control back - you close the laptop, the Wi-Fi drops, the program is killed - the adapter is supposed to work out on its own that nobody is there any more and start logging again. It waits about 80 seconds, checks that the tool is really gone, and resumes.

That safety net had a hole. Part of the check was **"the CAN bus has gone quiet for 300 milliseconds"**, and on a car with the key on the bus is never quiet - the engine computer is broadcasting thousands of messages a second. So the check never passed, and the adapter stayed on hold **forever**.

The bad part is how it looks while it happens. The adapter seems perfectly healthy: Wi-Fi connected, SD card mounted, mode showing Datalogger, no errors anywhere. It is simply recording nothing. You would only find out later, when the log file for that drive is empty.

Restarting NC Flash cleared it, and so did rebooting the adapter. Nothing else did.

## The fix

The adapter was asking the wrong question. "Is the bus silent?" was never going to be true on a running car. What it actually needs to know is **"is anyone in the middle of a conversation with the engine computer?"** - which is a much smaller, much quieter kind of traffic, and it does stop.

So it now watches only diagnostic messages: the ones the adapter sends, and the engine computer's replies. Normal engine broadcasts are ignored. Everything else about the safety net is unchanged.

The check was made narrower, **not removed**. It is what stops the adapter barging into a conversation someone else is having with your ECU - a workshop scan tool plugged in alongside it, for instance. That protection is still there.

## How it was tested

On a real engine computer with the ignition on and the bus busy:

- **Tool abandoned mid-session** - the adapter resumed on its own after **78.9 seconds** and opened a fresh log file. Throughout the test the old "is the bus quiet" measurement never rose above 10 milliseconds, which is exactly why the old code could never act on it.
- **Datalogger paused and abandoned** - resumed after about 13 seconds.
- **Manual override** - the "release the bus" and "resume" commands still work with no session token, and can be sent twice safely.

Two checks were **not** run on hardware and are worth naming: the same test with the ignition off, and a full normal flash confirming the adapter never resumes in the middle of one. That second one is protected by two separate locks in the code, both reviewed line by line, but neither was exercised on the bench for this release.

## What did not change

Nothing on the PC side. No timing values moved, no settings changed, and NC Flash needs no update - old versions and new ones both behave exactly as before.

## Install

**Over Wi-Fi (recommended):** open the device page, go to **System > Update Firmware**, upload `wican-fw_obd_pro_v1_22_2.bin`.

**Over USB (serial):** `bootloader.bin` at `0x0`, `partition-table.bin` at `0x8000`, `ota_data_initial.bin` at `0xd000`, `wican-fw_obd_pro_v1_22_2.bin` at `0x10000`.

## Honest notes

**A diagnostic session run through the external OBD chip is still invisible to this check.** In ELM327 and AutoPID modes the adapter's own CAN controller is not used at all, so it cannot see that traffic. That was equally true before this release - it is a long-standing limit, not a new one.

**If diagnostic traffic never stops, the adapter will stay paused - on purpose.** A wedged ECU, or a workshop tool left plugged in, both look like "someone is still using the bus". Resuming into that is the thing the check exists to prevent. Use the manual resume if you hit it.

**Fault-code reads and ROM reads still leave no trace in the log.** You will see that a host claimed the bus, not what it did with it.
